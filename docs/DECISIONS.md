# Decisions

Decisions made while executing docs/BUILD_SPEC.md that the spec left to us, recorded with one line of reasoning each, newest first.

## Phase 1 (provider model IDs and pricing config — research only, API keys still needed for real calls)

- **The evaluation model is `gemini-4-argon`, not "Gemini 3.5 Flash."** BUILD_SPEC Part 2 names "Gemini 3.5 Flash (configurable, chosen by the eval harness)," but as of 2026-10-18 no model with that exact name exists on Google's own model catalog (https://ai.google.dev/gemini-api/docs/models) — Google's naming has moved on since the spec was written, and the real nearby names are `gemini-3.5-flash-lite` (a cheaper lite variant, not a plain "Flash" model) and the newer `gemini-3.8-flash`/`gemini-4-argon`. Per the eval harness's own "configurable" framing and the instruction to pick "reasoning-capable, not necessarily the cheapest," this build picked `gemini-4-argon` — Google's own docs call it "our flagship reasoning model, built for complex software engineering, deep mathematical and scientific problem solving, autonomous multi-step agents," and it supports structured JSON output (needed for the scored-with-evidence report schema in Part 4.5 step 8) and thinking at low/medium/high levels. It is also genuinely new (GA via the Gemini API on 2026-10-13, five days before this was confirmed) and 5-10x more expensive per token than the Flash tier, so `gemini-3.8-flash` (also stable, also thinking-capable, materially cheaper) is wired as a documented fallback behind the same `configurable` flag in `services/engine/app/config/models.yaml` rather than being deleted — swap to it first if Argon proves rate-limited, unstable, or too costly once real evaluation volume exists.
- **Provider prices in `services/engine/app/config/pricing.yaml` are stored as paise-per-unit floats, converted from USD at a single pinned snapshot rate (1 USD = 95.029 INR, xe.com mid-market, captured 2026-10-18)**, rather than fetching a live rate at request time or storing USD alongside INR. BUILD_SPEC Part 5 defines `usage_events.cost_paise` as a plain `int` column with no currency/rate column next to it, so a point-in-time approximate rate (clearly dated and sourced in the file, with a note to revisit it) is the simplest thing that matches that schema; a live-FX dependency on every provider call would add a failure mode and nondeterminism the spec never asked for. Sarvam's prices are already published in INR and bypass this conversion entirely.

## Phase 5 (college admin dashboard, Part 4.7 — no AI involved, built fully real)

- **The college admin dashboard's role guard (`lib/auth/require-college-admin.ts`) only lets `role === "college_admin"` through, not `platform_admin` too**, even though `lib/auth/nav-config.ts` already gives `platform_admin` the same Students/Invites nav links (it inherits everything `college_admin` sees). Every query on these pages relies on RLS scoping rows to `current_user_college_id()`, which is `null` for a `platform_admin` by design (no single college) — letting one through here would just show them an empty dashboard, not a real cross-college view. Cross-college tooling for `platform_admin` is separate, later work (Part 4.8's Colleges page), not this slice.
- **`/app` itself (already every role's sidebar-logo link) doubles as the college_admin's Overview page, instead of adding a new `/app/overview` nav entry.** `lib/auth/nav-config.ts`'s `COLLEGE_ADMIN_NAV` already matches Part 4.1's literal "college_admin: + Students, Invites" phrasing exactly (no third entry); `app/app/page.tsx` already existed as every role's placeholder home screen, so branching it by role (`CollegeAdminOverview` for `college_admin`, the existing placeholder otherwise) reuses that instead of inventing a nav link the spec never asked for.
- **`interview_reports.overall_score`'s scale is assumed to be 0-100** for the Overview/Students readiness bands (`lib/readiness.ts`: ≥75 "Ready", ≥50 "Developing", else "Needs practice", `null` "Not yet assessed"). BUILD_SPEC Part 4.7 asks for a "readiness distribution" but never defines readiness numerically, and the evaluation harness that will actually produce `overall_score` is Phase 1/4 work, still blocked on provider keys. Chose 0-100 to match `eye_contact_pct`/`posture_stability_pct`'s own `numeric(5,2)` "pct" columns on the same table — revisit once the real evaluation prompt fixes the actual scale.
- **Every embedded-relation Supabase select (e.g. `profiles.select("..., batches(name)")`) needs a manual type assertion to a hand-written interface, and a long select string must be one literal (a no-interpolation template literal is fine; `"a" + "b"` string concatenation is not).** Neither is a judgment call so much as a hard requirement of this project's existing setup: `lib/supabase/client.ts`/`server.ts` pass no `Database` generic to `createClient()` (same as every other query in the codebase — see `lib/auth/current-profile.ts`'s own `as Profile` cast), so `@supabase/postgrest-js`'s type-level select-string parser (new since ~v2.45, ships in the installed `^2.118.0`) can't resolve a foreign table's real cardinality and infers an array even for a true many-to-one embed; and that same parser collapses to a `GenericStringError` placeholder type the instant the select string isn't a literal type (string concatenation widens to plain `string`), breaking every property access on the result. Found by `npm run typecheck` failing on exactly these two patterns across `app/app/students/page.tsx`, `app/app/students/[id]/page.tsx`, and `app/app/invites/page.tsx`.
- **Invites' "resend" action re-arms the existing token (extends `expires_at` by 14 days, flips an `expired` row back to `pending`) and copies the same `/onboarding?token=...` link to the admin's clipboard, rather than sending an email.** No email provider is wired up for invites (only `demo_requests` has a working Resend integration, per Phase 2's progress notes) — a "Resend" button that silently claimed to re-email the student would be exactly the kind of invented behavior BUILD_SPEC Part 6 forbids. This is still a fully real, non-stubbed write (an actual `invitations` UPDATE under the admin's own RLS-checked session); the admin shares the copied link themselves.
- **The CSV invite uploader inserts valid rows one at a time (sequential `await`s), not as a single multi-row `insert([...])` call**, specifically so a bad row's unique-constraint violation (duplicate pending invite for the same email) fails only that row instead of rejecting the whole batch — matching Phase 5's own acceptance criterion ("CSV invite with deliberately bad rows shows row-level errors"). Slower for a large file, but college invite batches are not at a scale where that matters.
- **Live-fixture RLS verification (creating temporary auth.users/profiles/interviews rows in the real `rhynjyamkeqsdvymmzhc` project, as Phase 2 did to prove RLS itself) was deliberately not repeated for this slice.** Checking `auth.users` before writing anything found it is no longer empty — the founder's own real account (`sreeadithya.ndd@gmail.com`, role `student`, no college yet) now exists in this live project. These pages don't change any RLS policy, only consume the already-verified ones, so verification instead leaned on: a full manual cross-check of every query's table/column/embed against a live `list_tables` call (not just the migration files), `npm run lint`/`typecheck`/`build`/`test` all passing, and fetching `/app/students`, `/app/invites`, and `/app/students/<id>` from a running `next dev` instance unauthenticated to confirm the shared `app/app/layout.tsx` guard still redirects to `/login` for all three. The authenticated-but-wrong-role branch (`requireCollegeAdmin` redirecting a signed-in student to `/app`) was verified by code review only, not a live session — doing so would need either a real college_admin login or new test fixtures in that same now-occupied project.

## Phase 4 (AI interview UI, providers still blocked)

- **Added three more `SECURITY DEFINER` functions (`create_stub_interview`, `start_stub_interview`, `record_stub_interview_turn`, `finish_stub_interview`) instead of INSERT/UPDATE policies on `interviews`/`interview_turns`/`interview_reports`.** Same situation and same reasoning as `create_stub_resume_scan(...)` above: those three tables deliberately have no authenticated write policy ("the engine's service role is the only writer" / "written by the engine on report completion"), there is still no service-role key in this environment, and the real engine doesn't exist yet. Each function always writes `auth.uid()`'s own interview (checked by `user_id`/ownership lookup before any write) and the report is explicitly tagged `model_id = 'stub-fixture-v1'` so it can never be mistaken for a real evaluation. Applied live as `supabase/migrations/20261017180000_interview_stub_bridge.sql`. **TODO(phase-1):** drop all four once the real engine (service role) exists and have it write these tables directly, matching the eventual path for `resume_scans`/`chat_messages`.
- **The separate `weak_areas` table is not written by the stub interview flow.** The report page reads weak areas straight from `interview_reports.weak_areas_summary` (a jsonb column that already exists for exactly this), which is enough to render the report per BUILD_SPEC Part 4.5 step 9. Writing the normalized `weak_areas` table too (so it feeds a future "practice recommendations" surface) is real-engine work — BUILD_SPEC Part 4.5 step 8 frames it as something the evaluation step writes back, not something a stub should fabricate a second copy of.
- **`eye_contact_pct`/`posture_stability_pct` are always saved as `null` from the stub flow**, rather than inventing plausible-looking numbers. BUILD_SPEC Part 4.5 step 7 ("MediaPipe runs in the browser and sends only aggregate metrics") describes a real browser-side measurement; fabricating a number for something that reads as a biometric measurement would cross the line this build explicitly draws ("never claim a mock result is real"), unlike a question/transcript/score that's already clearly badged as preview content.
- **Silero VAD assets (`@ricky0123/vad-web`'s ONNX model + AudioWorklet bundle) are loaded from the jsdelivr CDN at runtime (`baseAssetPath`/`onnxWASMBasePath`), not copied into `apps/web/public/`.** The package's default asset-path resolution relies on `document.currentScript`, which is `null` when the package is loaded as an ES module through Next's bundler (it's built for a plain `<script>` tag), so an explicit path is required either way; pointing it at the CDN avoids vendoring an ONNX binary and this package's own worklet bundle into the repo for a feature that's already explicitly a provider-independent, browser-only piece.
- **The stub engine's stage/turn plan (`lib/interview/constants.ts`'s `STUB_TURN_PLAN`) is hardcoded, not read from `interview_templates`.** That table is real and queryable (`SELECT` for any authenticated user) but unseeded in this environment (0 rows) — BUILD_SPEC Part 7's seed data was never part of any phase done so far. A hardcoded 10-turn plan (one deliberate follow-up included, to exercise that path) is simpler and doesn't depend on seed data existing; swap in a real `interview_templates` read once a template row exists.
- **Recorded answer audio is kept in an in-memory, per-browser-tab store (`lib/interview/audio-store.ts`) instead of uploaded anywhere**, matching `create_stub_resume_scan`'s precedent of not inventing storage that doesn't exist. There is no R2 (or other) upload wired up, so `interview_turns.answer_audio_key`/`question_audio_key` are always left `null`. The room and report page share this store so a just-recorded clip still plays back on the report page in the same session (lost on a full reload) — chosen over skipping playback entirely, since BUILD_SPEC Part 4.5 step 9 explicitly asks for "full transcript with audio playback per answer" and the recording itself is real, only its persistence isn't.

## Phase 3 (resume builder and scanner UI, Gemini/OCR still blocked)

- **Added one new SECURITY DEFINER function, `create_stub_resume_scan(...)`, instead of an INSERT policy on `resume_scans`.** The live schema deliberately has no authenticated INSERT/UPDATE policy on `resume_scans` ("a scan is produced by the engine... service role... billable action", per `20261015120007_row_level_security.sql`), and this environment still has no service-role key (same constraint as `accept_invitation`). Since the scanner currently only ever writes clearly-labeled mock data (`lib/ai-stubs/scan-resume.ts`) and nothing billable exists yet to protect, a narrowly-scoped function that always writes `auth.uid()` and validates any `resume_id`/`job_description_id` ownership before inserting (same shape as `accept_invitation`) lets the save/list/history flow be real against the real table without weakening the RLS model. Applied live as `supabase/migrations/20261017170000_resume_scan_stub_bridge.sql`. **TODO(phase-1):** once the FastAPI engine has a service-role key and actually calls Gemini/OCR, drop this function and have the engine insert directly, matching `interviews`/`interview_reports`/etc.
- **Resume data is stored as a JSON Resume-shaped object** (`basics`, `work`, `education`, `projects`, `skills`, `certificates`, `awards` — see `lib/resume/types.ts`), per BUILD_SPEC Part 4.3 ("JSON Resume schema"), not the reference Lovable site's bespoke `ResumeData` shape (`personalInfo`/`careerInfo`/`experience`/`achievements`...). Only the reference's *flow and visual patterns* (step-based questionnaire, live preview, template cards) were ported; the data model was redone to match the real `resumes.data` column's documented contents.
- **PDF export renders selectable text with `jspdf`'s own text/layout API (no `html2canvas`).** The reference site's PDF path isn't visible from its template components, but BUILD_SPEC Part 4.3 explicitly requires "real selectable text, no tables, no text in images" for ATS safety — `html2canvas` rasterizes the DOM into a bitmap embedded in the PDF, which is exactly the "text in images" failure mode the spec forbids. `jspdf`'s `doc.text(...)` calls lay out real PDF text objects instead.
- **The scanner reads an uploaded PDF's byte size/filename only; it does not store the file or extract its text.** Real text extraction needs Gemini/OCR (Part 7 Phase 1, blocked on API keys) and there is no Supabase Storage bucket provisioned for resumes yet. Storing an unparsed binary nobody can read yet would be dead weight; the upload path exists in the UI (and feeds the mock stub a plausible filename/size) so the real engine integration can slot in without a UI rewrite.
- **The resume scanner never computes or shows a single ATS score.** BUILD_SPEC Part 4.4 explicitly forbids this ("No universal ATS score exists, and placement officers know it"), even though the reference Lovable site's `ResumeScanner.tsx` has exactly that gauge — deliberately not ported.

## Auth foundation (login/signup, callback, onboarding, app shell)

- **`accept_invitation(p_token)` does not require `invitations.email` to match the caller's own auth email.** The 32-random-byte token is already the real bearer secret an invite link/code carries (unguessable, single-use, revocable on accept); an exact-email check on top would reject the ordinary case of a student signing up with a different address than the one a college admin typed when inviting them. Defined `SECURITY DEFINER` instead of attempting a service-role bypass (no service-role key exists in this environment) — see `supabase/migrations/20261017160000_accept_invitation.sql`'s header comment for why that's safe against the self-escalation guard trigger.
- **Supabase grants a new function's `EXECUTE` to `anon`/`authenticated`/`service_role` directly (via its own default privileges), not through the `PUBLIC` pseudo-role** — `revoke all ... from public` alone left `anon` still able to call `accept_invitation`. Confirmed live via `get_advisors(type: "security")` (the `anon_security_definer_function_executable` finding) and fixed with an explicit `revoke all on function public.accept_invitation(text) from anon;`.
- **Route protection for `/app` lives in `app/app/layout.tsx` (a Server Component check), not in `proxy.ts`/`lib/supabase/middleware.ts`.** One guard already covers every nested page via Next's layout nesting, and every page under `/app` makes its own Supabase round trip anyway, so a second check in middleware would add latency with no real safety benefit. `middleware.ts` keeps doing only session-cookie refresh, as it already did.
- **The app shell's nav items are read as cumulative by role** (`student` ⊂ `college_admin` ⊂ `platform_admin`) per `docs/BUILD_SPEC.md` Part 4.1's "college_admin: + Students, Invites" phrasing — implemented as one array per role built by spreading the previous role's array, in `lib/auth/nav-config.ts`, rather than three independent lists that could drift.

## Phase 2 (schema pushed to a real project — genuine RLS verification)

- **All 7 migrations plus one hardening migration were applied to a real Supabase project (`rhynjyamkeqsdvymmzhc`, "Vyoman-AI-Interviewer") and RLS was verified against live data, not just reviewed statically.** Every one of the 7 original files applied with zero errors on the first real run. Three real, live-only findings came out of this:
  1. **Supabase auto-enables RLS on every new `public` table** via its own `rls_auto_enable()` event trigger (not something any of our migrations do). This silently blocked the `GRANT SELECT` the original migration relied on for `question_bank`, `interview_templates` and `plans` — RLS-enabled-with-no-policy denies all non-owner access regardless of grants. Fixed in `20261017150000_advisor_hardening.sql` by adding an explicit `SELECT` policy to each of those three (the other three grant-only tables, `kb_documents`/`kb_chunks`/`tts_cache`, were meant to have zero anon/authenticated access anyway, so the auto-enabled policy-less RLS on them was already correct by accident).
  2. **Nine `SECURITY DEFINER` helper/trigger functions were reachable by `anon`/`authenticated` via PostgREST's auto-exposed `/rest/v1/rpc/<name>`.** Several (`profile_college_id`, `interview_owner_id`, `interview_college_id`, `chat_session_owner_id`) take an arbitrary id and return ownership/college data for *any* row by design, so calling them directly (not through a policy) would leak that mapping for a guessed/enumerated id — a real information-disclosure risk. Fixed by moving all nine into a new `private` schema (via `ALTER FUNCTION ... SET SCHEMA`, which PostgREST doesn't expose by default) rather than revoking `EXECUTE`, since revoking would also have broken the RLS policies that legitimately call these functions.
  3. **That same schema move broke `is_platform_admin()` and `is_college_admin()`, and this is the more important lesson:** their function bodies called `public.current_user_role()` by explicit text reference. RLS *policy* expressions resolve function calls to a fixed OID at creation time, so moving a function's schema leaves existing policies working unchanged — but a `LANGUAGE SQL`/`plpgsql` function *body* re-resolves a schema-qualified name by catalog lookup on every call, not by a frozen OID. Moving `current_user_role()` to `private` silently broke every other function whose body still said `public.current_user_role()`, which only surfaced as a live `function ... does not exist` error during the first real RLS test — no static review would have caught this. Fixed by updating those two function bodies to call `private.current_user_role()`.
- **RLS was verified with real fixtures and real simulated sessions (`SET LOCAL ROLE authenticated; SET LOCAL request.jwt.claims = '{"sub":"<uuid>",...}'`), not just read by eye.** Created two colleges, five `auth.users`/`profiles` rows (two students in college A, one in college B, one college_admin for college A, one platform_admin), a resume and an interview per student, then confirmed: a student sees only their own resume/interview/profile; a college_admin sees every student's interview in their own college but none from the other college; a platform_admin sees everything; and a student attempting to self-escalate `role`/`college_id`/`batch_id` via a direct `UPDATE` is blocked by `guard_profile_privilege_columns()` with the exact intended error. All test fixtures were deleted afterward — the project is back to an empty, pristine state.

## Phase 2 (data model: schema + RLS, written before a live project existed)

- **`profiles` has no CHECK constraint enforcing "every student has a college_id and batch_id."** A brand-new student signs up (email OTP / Google) before any college is known; that CHECK would make `handle_new_user()`'s insert fail on every signup. The invariant is an onboarding-completion rule enforced when an invitation is accepted, not a table constraint — documented in a comment on the `profiles` table (migration `20261015120001_core_tenancy.sql`).
- **Every write that implies a billable provider call (interviews, interview_turns, interview_reports, weak_areas, resume_scans, chat_messages, usage_events, payments) has no INSERT/UPDATE policy for the `authenticated` role.** Those rows are only ever written by the FastAPI engine using the Supabase service role (which bypasses RLS), after it has checked quota and actually called the provider — letting an authenticated client insert/update them directly would let it fabricate a report, a cost-free "interview," or a captured payment. Plain data-entry tables with no provider cost (resumes, job_descriptions, chat_sessions) keep ordinary owner CRUD.
- **`question_bank`, `interview_templates`, `kb_documents`, `kb_chunks`, `plans` and `tts_cache` have no row level security at all** (per the task's explicit instruction for `question_bank`/`plans`, generalized to the other four platform-curated/reference tables). Supabase's default per-table grants to `anon`/`authenticated` are explicitly revoked for writes (and, for `kb_documents`/`kb_chunks`/`tts_cache`, for reads too) instead, so even platform_admin edits to these go through the engine's service role rather than a direct browser-JWT write. See the header/footer comments in `20261015120007_row_level_security.sql`.
- **`college_id` is denormalized onto `interviews`, `interview_reports`, `weak_areas`, `chat_sessions` and `usage_events`** (set from the owning profile at creation time) so the college_admin dashboard and its RLS policies can filter by college directly instead of joining through `profiles` on every row. `resumes`/`resume_scans`/`job_descriptions` were left without it: `resume_scans`/`job_descriptions` have no college_admin visibility at all per Part 4.7's literal scope ("reports and resume" only), and `resumes`' college_admin policy instead calls a small `profile_college_id()` helper.
- **RLS helper functions (`current_user_role()`, `current_user_college_id()`, `is_platform_admin()`, `is_college_admin()`, and a few parent-lookup helpers) are `SECURITY DEFINER`.** Without that, a policy on `profiles` calling a function that queries `profiles` would recurse against `profiles`' own RLS. Running as the function owner (which owns and is therefore exempt from RLS on `profiles`) avoids that and keeps every policy a single function call instead of a repeated subquery.
- **`quotas` uses two partial unique indexes (`where scope = 'user'` / `where scope = 'college'`) instead of one composite UNIQUE constraint.** A composite UNIQUE constraint treats NULL `user_id`/`college_id` values as always distinct, so it would silently allow duplicate college-scope quota rows.
- **This schema was never run against a live Postgres/Supabase instance** — no Docker, local Postgres, or cloud project was available. Verification was a full manual read of every statement plus a `sqlparse`-based tokenizer check (parens/quotes/semicolons balance, no tokenizer error tokens); see `supabase/migrations/README.md` for exactly what that does and doesn't prove.

## Phase 0

- **Root layout avoids Next.js 16's generated `LayoutProps<"/">` type; uses `{ children: React.ReactNode }` instead.** `LayoutProps` is ambient and only exists after `.next/types/` is generated by a build/dev run, so a standalone `tsc --noEmit` on a fresh clone (CI's exact scenario) fails before the first build. Caught by actually cloning the repo fresh and re-running the checks, not by trusting the in-place working copy.
- **Tailwind downgraded from v4 (create-next-app's default) to v3.4.17.** Tailwind v4 moved to a CSS-first `@theme` config and dropped `tailwind.config.ts` semantics; the reference site's tokens (HSL CSS variables, `@apply`-based utility classes, `tailwindcss-animate` plugin) port almost verbatim under v3 but would need a rewrite under v4. Revisit if a later phase specifically wants v4.
- **No monorepo tooling (no npm workspaces, no Turborepo/Nx).** `apps/web` and `services/engine` are two independent projects with their own install/run commands, matching the spec's own Phase 0 acceptance line ("web and engine both run locally with one documented command each"). Add real monorepo tooling only if a shared package actually emerges.
- **Engine dependencies are a plain `requirements.txt` + `requirements-dev.txt`, not Poetry/PDM.** Simplest thing that works for a single-service Python project; no multi-package dependency resolution problem to justify a lockfile-based tool yet.
- **Supabase `config.toml` was hand-authored, not generated via `supabase init`.** The Supabase CLI isn't installed in this environment. The hand-written file matches the standard CLI format (ports, `[auth]`/`[storage]` blocks) closely enough to scaffold Phase 0; it should be regenerated/reconciled once someone runs the real CLI (`npm i -g supabase && supabase init`) in Phase 2.
- **`eval/` and the `interview/resume/chat/reports/providers/costs` packages inside `services/engine/app/` are empty placeholders (just `__init__.py`).** The repo layout in Part 3 names these as decided structure, but writing real logic into them now would be building ahead of Phase 1/3/4/5/6, which is what actually defines their contents.
- **Vitest + React Testing Library chosen over Next's built-in Jest setup for `apps/web`.** Jest's integration with Next 16 / React 19 is newer and fiddlier to get green fast; Vitest needed less configuration for one smoke test.
- **The founder's previous product (Lovable/Vite, at github.com/SreeAdithya123/Vyoman-interviewer) was cloned and its design-relevant source copied into `reference/lovable-site/`, excluding `.env`, `.git`, and Lovable's own `.lovable`/`.claude` config.** It is the *previous*, real-time-ElevenLabs-voice version that Part 1 of the spec explicitly says lost money and is being replaced — only its design tokens (colors, type, components) are reused, never its architecture (ElevenLabs/HeyGen edge functions, old Supabase schema).
